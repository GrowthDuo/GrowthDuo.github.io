Selenium简介

Selenium 是支持 web 浏览器自动化的一系列工具和库的综合项目。

通过它，我们可以写出自动化程序，像人一样在浏览器里操作web界面。 比如点击界面按钮，在文本框中输入文字 等操作。

Selenium 的核心是 WebDriver，这是一个编写指令集的接口，可以在许多浏览器中互换运行。 这里有一个最简单的说明：

显示等待

显示等待：指定一个等待条件（元素），在一定时间间隔内检测一次元素，程序会判断在等待时间内条件是否满足条件，如果满足则执行下一步，如果不满足会继续等待，超过时间就会抛出异常

导入WebDriverWait和expected_conditions包，调用until()者until_not()方法
　　
通过selenium.webdriver.suppert.ui模块提供的WebDriverWait类，再结合该类的until()和until_not()的方法，并自定义好等待时间，根据判断条件进行灵活等待。显式等待比隐式等待更节约执行时间，因此更推荐使用显式等待方式判断页面元素是否存在

WebDriverWait，配合该类的until()和until_not()方法，就能够根据判断条件而进行灵活地等待了。它主要的意思就是：程序每隔xx秒看一眼，如果条件成立了，则执行下一步，否则继续等待，直到超过设置的最长时间，然后抛出TimeoutException

上例中，我们设置了隐性等待和显性等待，在其他操作中，隐性等待起决定性作用，在WebDriverWait…中显性等待起主要作用，但要注意的是：最长的等待时间取决于两者之间的大者，此例中为20，
如果隐性等待时间 > 显性等待时间，则该句代码的最长等待时间等于隐性等待时间。

wait模块的WebDriverWait类是显性等待类，先看下它有哪些参数与方法：
selenium.webdriver.support.wait.WebDriverWait（类）

element=WebDriverWait(driver,5,0.5),until(EC.presence_of_element_located((By.ID,‘su’)))
element=WebDriverWait(driver,5,0.5).until(EC.presence_of_element_located(locator))

init
driver: 传入WebDriver实例，即我们上例中的driver
timeout: 超时时间，等待的最长时间（同时要考虑隐性等待时间）
poll_frequency: 调用until或until_not中的方法的间隔时间，默认是0.5秒
ignored_exceptions: 忽略的异常，如果在调用until或until_not的过程中抛出这个元组中的异常，则不中断代码，继续等待，如果抛出的是这个元组外的异常，则中断代码，抛出异常。默认只有NoSuchElementException

多种断言方法

  • unittest框架提供了多种断言方法，用于在测试用例中验证不同的条件。与比较运算符相对应的一些常见断言方法包括：

    • self.assertEqual(a, b)：检查 a == b 是否为True

    • self.assertNotEqual(a, b)：检查 a != b 是否为True

    • self.assertGreater(a, b)：检查 a > b 是否为True

    • self.assertGreaterEqual(a, b)：检查 a >= b 是否为True

    • self.assertLess(a, b)：检查 a < b 是否为True

    • self.assertLessEqual(a, b)：检查 a <= b 是否为True

测试套件 加载测试 测试的运行

多个测试用例可以组成一个 测试套件，由测试加载器来加载运行 。

  • test runner : 测试的运行

  • test loader : 加载测试

  • test suite : 测试套件（套件间可以嵌套）
    - 测试加载器并添加到测试套件中 : loadTestsFromTestCase(类名)
    - 模块加载 并添加到测试套件中 ： loadTestsFromModule(类名)

测试套件的使用

  1. 需要先创建一个加载器的对象，该对象用于从测试类中加载测试。

  2. 创建一个测试套件对象，该对象用于存放和管理所有的测试。

  3. 使用测试加载器加载所有的测试，并添加到测试套件中，这里有两种方案。

    1. 测试加载器并添加到测试套件中 : loadTestsFromTestCase(类名)
    2. 模块加载 并添加到测试套件中 ： loadTestsFromModule(类名)

  4. 创建一个文本测试运行器对象。该对象负责执行测试套件中的所有测试。

  5. 运行测试套件中的所有测试，并将结果输出到控制台。

两种方法区别
  • 测试加载器并添加到测试套件中 : loadTestsFromTestCase(类名)
  • 模块加载 并添加到测试套件中 ： loadTestsFromModule(类名)

在Python的unittest框架中，loadTestsFromTestCase和loadTestsFromModule这两个方法用于加载测试用例并添加到测试套件中，但它们之间存在一些重要的区别：

  1. 测试用例来源：
    • loadTestsFromTestCase(类名)：这个方法从指定的测试用例类中加载所有的测试方法。这意味着你需要手动在测试类中定义测试方法，并使用unittest.TestCase作为基类。
    • loadTestsFromModule(类名)：这个方法从整个模块中加载测试。它会在指定的模块中查找所有的测试方法（通常是以test_开头的方法），并将它们添加到测试套件中。这适用于模块级别上的测试。
  2. 灵活性：
    • 使用loadTestsFromTestCase时，你需要显式地定义每个测试方法。这允许你对每个测试用例进行详细的配置和设置。
    • 使用loadTestsFromModule时，你可以在模块的任何位置定义测试方法，并且它们会自动被发现和加载。这使得测试的组织和编写更加灵活。
  3. 场景：
    • 当你需要编写和组织多个独立的测试用例时，可以使用loadTestsFromTestCase。这适用于对特定功能或类的详细测试。
    • 当你希望在一个模块中对多个功能或类进行测试时，可以使用loadTestsFromModule。这适用于模块级别的集成测试或系统测试。
  4. 性能：
    • 对于每个类，使用loadTestsFromTestCase会单独加载和运行该类的所有测试。这可能会导致运行时间较长，特别是当有大量独立的测试类时。
    • 使用loadTestsFromModule会一次性加载和运行整个模块中的所有测试。这通常比逐个加载和运行每个测试类更快。
  5. 目的：
    • loadTestsFromTestCase主要是为了支持对单个测试类进行详细配置和设置。它允许你针对特定的功能或行为编写独立的测试用例。
    • loadTestsFromModule是为了在整个模块级别上组织和运行多个相关的测试用例。这有助于确保整个模块或系统的功能正常工作。

总的来说，选择使用loadTestsFromTestCase还是loadTestsFromModule取决于你的测试需求和场景。根据你的具体需求，你可以选择最适合的方法来组织和运行你的单元测试。

日志

日志的作用
  • 程序调试
  • 了解程序运行是否正常
  • 故障分析与问题定位
  • 用户行为分析 *
日志的等级
  • DEBUG 最详细的日志信息，典型应用场景是问题诊断。
  • INFO 信息详细程度仅次于 DEBUG，通常只记录关键节点信息，用于确认一切都是按照我们预期的那样进行工作。
  • WARNING 当某些不期望的事情发生时记录的信息（如 磁盘可用空间较低）， 但是此时应用程序还是正常运行的。
  • ERROR 由于一个更严重的问题导致某些功能不能正常运行时记录的信息。
  • CRITICAL当发生严重错误，导致应用程序不能继续运行时记录的信息。

logging 模块的使用

  • 第一种方式是使用 logging 提供的模块级别的函数

    • import logging
# 这将使日志输出类似于 "2023-07-19 12:34:56,789 - INFO - info" 的格式。
logging.basicConfig(level=logging.INFO, format='%(asctime)s - %(levelname)s - %(message)s')

 
# 设置日志记录的基本配置，指定日志级别为 INFO。
# 这意味着只有级别为 INFO、WARNING、ERROR 和 CRITICAL 的日志才会被记录。
# DEBUG 级别的日志将被忽略，因为 INFO 级别比 DEBUG 级别高。
logging.basicConfig(level=logging.INFO)



# 记录一条 INFO 级别的日志。由于我们设置了日志级别为 INFO，所以这条日志会被记录。
logging.info('info')  # 注意：这里 'infor' 可能是 'info' 的拼写错误

# 记录一条 DEBUG 级别的日志。由于 DEBUG 级别低于我们设置的 INFO 级别，所以这条日志不会被记录。
logging.debug('debug')

# 记录一条 WARNING 级别的日志。WARNING 级别高于或等于 INFO 级别，所以这条日志会被记录。
logging.warning('warning')

# 记录一条 ERROR 级别的日志。ERROR 级别高于 INFO 级别，所以这条日志会被记录。
logging.error('error')

# 记录一条 CRITICAL 级别的日志。CRITICAL 是最高的日志级别，所以这条日志会被记录。
logging.critical('critical')

Selenium Grid中心模式（Hub & Node）

Hub（主控制节点）

Hub 是 Selenium Grid 的中心控制节点，负责管理和分发测试请求。Hub 接收来自测试脚本的请求，然后将这些请求分发给连接到 Grid 的各个 Node 上执行。

功能：

  1. 管理测试分发： Hub 负责将测试分发给 Grid 中可用的 Node。

  2. 维护节点信息： Hub 会维护连接到它的各个 Node 的信息，包括节点的浏览器类型和版本。

  3. 处理测试结果： Hub 负责收集并汇总各个 Node 返回的测试结果。
